## How to reproduce

### Prerequisites

- Node 20.x and the repo's normal dev deps (`npm install` at repo root).
- Claude Code CLI on `$PATH` (`claude --version`).
- `doc-wiki` plugin installed: `claude plugin install narailabs/doc-wiki` (or local symlink during dev).
- Per-repo language toolchains: `python3.11`, `pyenv`/`venv`; Node 20 + `corepack`/`yarn`; `ruby 3.3` + `bundler`. The harness shells out to whatever's on `$PATH`.
- An Anthropic API key or active Claude Code Pro/Max session.
- A few hundred dollars in Anthropic credit (see cost estimate in `PLAN.md`).

### One-off: install harness deps

The harness reuses the repo's root `package.json` (`tsx`, `js-yaml`) — no separate install needed. From the doc-wiki repo root:

```sh
npm install
```

### Validate the manifest first (cheap, no money spent)

```sh
npx tsx benchmark/harness/validate.ts
```

For each `(repo, issue)`, this calls `gh api` to confirm the `fix_commit` exists in the upstream repo and the `test_path` resolves at that commit. Pass/warn/fail table. Run before any real benchmark so you don't burn money on a typo in `repos.yaml`.

### Mock the pipeline (cheap, no money spent)

```sh
npx tsx benchmark/harness/run.ts --mock
npx tsx benchmark/harness/score.ts
```

`--mock` generates deterministic synthetic per-run JSON (no clone, no Claude, no test). Useful to verify the run.ts → score.ts pipeline end-to-end, exercise the result schema, and sanity-check the headline table format before committing to a real run. Synthetic results are clearly labelled (`raw: { mock: true }` in each JSON).

### Run the benchmark for real — two modes

**Mode A: session-agent (canonical)** — the Claude Code session reads `repos.yaml`, dispatches one subagent per `(repo, issue, condition)` via the Agent tool, and each subagent does the full clone → install → optional atlas → fix → test → write JSON cycle. Token cost is billed against the host session's subscription, not a separate `claude -p` invocation. Methodology + prompt templates at [`dispatch.md`](dispatch.md).

**Mode B: subprocess (`claude -p`)** — `harness/run.ts` shells out to `claude -p "..."` for each issue. Older design; lower-overhead and easier to script, but requires the Claude Code CLI to have working auth and doesn't ride the host session's subscription. Use the commands below for Mode B.

From the repo root:

```sh
# All repos, all issues, both conditions (long-running, hours; spends real $)
npx tsx benchmark/harness/run.ts

# One repo only
npx tsx benchmark/harness/run.ts --repo django

# One issue, baseline only (smoke test, ~$1-3)
npx tsx benchmark/harness/run.ts --repo mastodon --issue 37652 --condition baseline

# Re-run a specific (repo, issue, condition) that's already been recorded
npx tsx benchmark/harness/run.ts --repo mastodon --issue 37652 --force
```

The smallest, sharpest issue for a smoke test is `mastodon/37652` (8 LOC fix, single regex change, one model spec). Run that one first to verify your local environment (Ruby 3.3, bundler, Postgres available for Rails tests) before scaling to the full suite.

The runner is **resumable**: it skips any `(repo, issue, condition)` triple whose result JSON already exists under `runs/`. Delete the file or pass `--force` to re-run.

### Aggregate results

After runs finish (or any time, with partial data):

```sh
npx tsx benchmark/harness/score.ts
```

Writes `results/RESULTS.md` and `results/raw.csv`.

## How to interpret

- **Success = the specific test added/modified in the fix PR passes after Claude's changes.** Binary. No partial credit, no LLM-judge.
- **Pre-existing test regressions** are recorded in `regressions` but don't fail the issue. A run can succeed-with-regressions; that's a separate column.
- **Cost / tokens / duration / turns** captured per run from Claude Code's `--output-format=json`. Use these for the cost-per-fix sub-narrative.
- **Atlas cost** is recorded once per (repo, with-docwiki) and amortized across the issues in that repo.

## How to add issues

Edit `repos.yaml`. Each issue needs:

```yaml
- id: <stable-id>            # GitHub issue number works
  title: <issue title>
  body: |
    <full issue body — what the maintainers saw>
  fix_commit: <full SHA>     # the merge commit of the fix PR
  test_path: <path::test>    # the specific test the fix PR adds/modifies
```

Selection rules in [`PLAN.md`](PLAN.md). V1 ships 2 placeholder issues per repo so the harness can be smoke-tested before the curated list is filled in.

## Caveats (read before quoting numbers)

1. **SWE-bench-style benchmarks test OSS, not enterprise messes.** The number measured here is a directional signal, not a guarantee on a private monolith. Mention this in any reporting.
2. **Single-run accuracy ≠ 8-run consistency.** Published agent benchmarks regularly show 60% → 25% degradation when re-run independently. Re-run the suite ≥3× and report median + spread, not single-run.
3. **Model drift.** Pin the model in `repos.yaml` (`defaults.model`). When Anthropic ships a new minor version, re-run the suite and version the results.
4. **Cherry-picked issues are tempting; don't.** The reviewer test: can a hostile commenter swap out the 20 chosen issues for 20 of their picks and reproduce the headline? Curate broadly enough that the answer is yes.
